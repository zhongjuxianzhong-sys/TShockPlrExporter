# SQLite/MySQL Runbook

## 适用范围

用于诊断 TShock 后端的识别、连接、读取兼容性、写入失败和超时问题。

## 后端选择

插件读取 `tshock/config.json`：

- `StorageType` 为 `sqlite` 或空值时使用 SQLite。
- `StorageType` 为 `mysql` 时使用 MySQL。
- 其他非空值会提示不支持，插件目前只支持 SQLite 与 MySQL。

读取 `tsCharacter` 使用独立连接；SQLite 读取连接为只读模式。导入写回使用独立读写连接和事务。

## SQLite 检查

1. 确认服务器已启动并生成 `tshock/tshock.sqlite`，或确认配置指向自定义路径。
2. 检查 `SqliteConnectionString` 或 `SqliteDBPath` 是否相对 `TShock.SavePath` 正确解析。
3. 确认运行 TShock 的账号对数据库文件具有读取权限；导入还需要写入权限和目录权限。
4. 确认数据库没有被独占锁定或被其他工具以不兼容方式打开。

常见结果：

| 日志或现象 | 含义 | 处理 |
| --- | --- | --- |
| 未找到 TShock 的 SQLite 数据库 | 配置路径不存在 | 修正路径，或启动服务器生成数据库 |
| `SQLite Error 8` / read-only | 文件或目录权限不足、只读介质或锁冲突 | 停止写入，修复权限和磁盘状态后重试 |
| 查询超过 30 秒 | 数据库被锁、磁盘异常或服务器资源耗尽 | 检查锁持有者、磁盘 I/O 和服务器负载 |

## MySQL 检查

1. 优先检查 `MySqlConnectionString`；为空时插件会从分散的 `MySql*` 配置构造连接字符串。
2. 确认 `MySqlHost`、端口、数据库名、用户名和密码正确。
3. 确认 TShock 本身可以正常读写同一数据库。
4. 不要在聊天、工单或日志中粘贴连接字符串，因为它可能包含数据库密码。

常见结果：

| 日志或现象 | 含义 | 处理 |
| --- | --- | --- |
| `MySqlHost 为空` | StorageType 为 MySQL，但没有可用主机配置 | 补齐连接字符串或 MySQL 主机配置 |
| 连接超时 | 网络、DNS、防火墙或数据库负载问题 | 先用最小客户端验证连通性，再检查数据库负载 |
| 写入影响 0 行 | 目标账号状态或事务结果异常 | 不要重复盲写；检查 `Users`、`tsCharacter` 和事务日志 |

## 列兼容性

`tsCharacter` 的列可能随 TShock 版本增减。插件按列名读取，缺少预期列时使用默认值，并且每个服务器生命周期只提示一次缺列警告。

如果出现大量字段默认值，检查 TShock 版本和数据库迁移是否完整。不要通过调整列顺序或手工重建表绕过兼容检查。

## 安全要求

- 所有查询都使用参数；不要为排障临时拼接 SQL。
- 不要把数据库密码写入 AGENTS、runbook 或 issue。
- 大范围修复前先备份数据库。
- 若怀疑写入失败或事务未完成，先停止服务器并保留日志，再决定恢复步骤。
